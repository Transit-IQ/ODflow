# ODFlow — GIS & Configuration Data

This folder contains all raw inputs consumed by `../apps/backend/scripts/build_dashboard_data.py`
(the static-dashboard pipeline) and `../apps/backend/` (the interactive dev API). It is gitignored
(besides this README and `gtfs/README.md`) — populate it locally per the instructions below.

## Contents

| Path | Format | Used for |
|---|---|---|
| `gtfs/agency.txt`, `routes.txt`, `trips.txt`, `stops.txt`, `shapes.txt`, `stop_times.txt` | GTFS text | Bus lines, stops, shapes, trip frequency (see `gtfs/README.md`) |
| `gtfs/BUS_SPEED/` | Shapefile | Per-segment bus speed by day-of-week × time-of-day (35 values/segment) |
| `gtfs/גבול העיר/` | Shapefile | Tel Aviv city-limits polygon, used to clip the speed segments |
| `neighbourhoods.json` | JSON | Config: the 19 selectable neighbourhoods (id, Hebrew name, center, bbox) — an input parameter, not derived data |
| `neighbourhood_boundaries.json` | JSON | Real boundary polygons for 13 of the 19 areas, fetched once from OpenStreetMap Nominatim — see below |

## Coordinate System

GTFS files are already WGS-84. The shapefiles are in ITM (EPSG:2039); the pipeline converts them via
`backend/services/gis_loader.itm_to_wgs84`.

## `neighbourhood_boundaries.json`

`neighbourhoods.json`'s `bbox` values were hand-drawn rectangles, always noticeably larger than the
neighbourhood they represent — for two of them the box didn't even overlap the real area at all. To
fix this, `neighbourhood_boundaries.json` holds real boundary polygons (`{ "<neighbourhood id>":
<GeoJSON Polygon/MultiPolygon> }`) fetched once from OpenStreetMap's Nominatim API, for the 13 of 19
areas that are real, officially-recognized neighbourhoods with an OSM boundary relation. It is **not**
regenerated by the pipeline automatically (that would add a live external dependency to what's
supposed to be an offline, "run once locally" step) — if you need to refresh it or add coverage,
re-run the same Nominatim query pattern used to build it (see git history) and drop the result here.

The remaining 6 areas (`merkaz` / city center, `rothschild` / a boulevard, `azrieli` / a shopping
complex, `jaffa`, and the two intentionally-informal `*_border` zones) aren't real polygons in OSM, so
they still fall back to their `bbox` rectangle in `neighbourhoods.json` — the frontend and pipeline
both know to do this when a given id has no entry here.

**Attribution**: boundary data is © OpenStreetMap contributors (ODbL). The basemap tiles this app
already uses (CartoDB) are also OSM-derived. The current UI disables Leaflet's attribution control
(`attributionControl: false` in `app.js`) — before any public/production deployment, re-enable
attribution or add equivalent credit; OSM's and CartoDB's usage terms require it.

## Missing data — dashboard sections currently hidden

The following dashboard sections were removed from the frontend (rather than shown with fabricated
numbers) because nothing in this folder backs them. Add the corresponding file(s) below and re-run
the pipeline to bring each one back:

### 1. Station Analytics panel (per-stop boardings & demographics)
The UI previously showed daily validations (תיקופים), stops served, and a passenger-demographic
breakdown per bus stop — all from an empty, hardcoded `STATIONS = []` array. Needed:
- A per-stop ridership file (e.g. `data/ridership/stations.csv`), keyed by `stop_id` (to join against
  `gtfs/stops.txt`), with: daily validations count, daily boarding count, hourly boarding counts for
  the buckets `04-06, 06-09, 09-12, 12-15, 15-19, 19-24, 24-04`, and a passenger-type breakdown
  (adult / elder / youth / disabled / student / other), plus % of trips that are pass-through vs.
  origin/destination at that stop.

### 2. Employment/commercial destination layer + desire lines
The "מוקדי תעסוקה ומסחר" and "צירי יעד עיקריים" map layers pointed at `D.dests`, which was never
populated by any fetch. Needed:
- A points-of-interest file (e.g. `data/poi/destinations.geojson` or `.csv` with lat/lon) of major
  employment/commercial hubs, each tagged with a category (used to pick "hub" destinations for the
  desire-line layer) and a Hebrew/English display name.

### 3. "Bus vs. car" travel-time KPI
The KPI card claiming a 2.6× / 39-vs-15-minute gap was a hardcoded string in `index.html` with no
backing computation. Needed:
- Scheduled bus travel time can be derived from existing GTFS `stop_times.txt` for a given
  origin/destination pair, but there is no **driving time** data source to compare against — e.g. a
  road-network travel-time matrix or an API-sourced driving-duration for the same trips.

### 4. Neighbourhood population figure
A "~13,000 residents" figure was hardcoded in the HaTikva flow-layer popup. Needed:
- A neighbourhood population/demographics file (e.g. CBS statistical-area data) joined to the
  `neighbourhoods.json` `id`s.

## Accessing raw data during development

The interactive backend (`../apps/backend/`, `uvicorn main:app --reload`) can query these files directly
via `/gis/*`, `/gtfs/*`, and `/layers/*` for exploration. The deployed dashboard does not use it —
see `../apps/frontend/README.md`.
